# v0.4.1 release notes

## Summary

v0.4.1 is an unpublished candidate built from the unreleased v0.4 operational-control work. It adds scheduled evidence, review prioritization, repository issue lifecycle, privacy fixes, supply-chain controls and capture-readiness checks. A separate owned functional example teaches and tests a simple cart flow; the Action itself remains a script/header evidence tool.

It does not contain or claim an approved third-party vendor adapter.

## Security and privacy fixes

- Reject non-2xx main documents in browser and static mode.
- Check expected final origin/path, including same-origin login/empty-cart redirects.
- Optionally check a stable page-ready element id; static mode requires presence and browser mode requires visibility.
- Capture errors exit 1 even with `--no-fail`; they cannot create a successful baseline, PASS or recovery alert.
- Page identity or readiness-policy changes require human review.

- CSP nonce values are redacted from selected stored headers.
- Query values in absolute and relative CSP report URLs are redacted.
- Requested-page, final-page, and external-script URL fingerprints are computed only after URL query-value redaction.
- Exact direct npm versions and lockfile integrity replace dependency ranges.
- CI and nested Actions are pinned to reviewed full commit SHAs.
- CI and Action dependency installation disable npm lifecycle scripts.
- Playwright invocation uses `npx --no-install`.
- CodeQL, dependency review, Dependabot, a threat model, and supply-chain documentation are included.

## Operational additions from v0.4

- Scheduled monitoring and configurable evidence retention.
- Machine-readable monitoring events and review-alert payloads.
- Optional deduplicated GitHub issue open/update/recovery lifecycle.
- P1/P2/P3 workflow review priorities, explicitly not vulnerability severities.
- Stronger approval, business-purpose, integrity-evidence, and expiry validation.
- Local `PASS -> P1 REVIEW_REQUIRED -> PASS` acceptance fixture.

## Release integrity

The published-release workflow verifies the version/tag match, installs locked dependencies, runs tests and the local lifecycle, creates a source archive and SPDX SBOM, computes SHA-256 checksums, and requests GitHub provenance and SBOM attestations.

The workflow must pass before the release is described as verified.

## Upgrade behavior

Configure `capture_expectations.expected_final_url` and a suitable `ready_element_id`. The final URL must contain no credentials, query or fragment and use an authorised origin. If omitted, the expected origin/path defaults to the configured URL; marker coverage is explicitly not configured. A same-origin redirect that previously succeeded may now correctly fail. An intentional redirect needs an explicit expectation.

The optional readiness marker and default page-identity checks do not prove that totals, payment processing or order creation work. Use separately scoped functional tests for those outcomes. GitHub commit metadata alone is not proof that the observed deployment was built from that commit.

Engine-version or capture-mode changes intentionally return `REVIEW_REQUIRED`. A team moving from an earlier release should:

1. test the new full-SHA Action revision on an authorized non-production target;
2. inspect all script, selected-header, origin, approval, and privacy-format changes;
3. verify the generated artifact digests;
4. approve a deliberate baseline replacement only after review; and
5. never regenerate a baseline automatically just to turn a result into `PASS`.

Because URL query values no longer influence URL fingerprints, a query-value-only URL change is intentionally excluded from the URL identity. A change in downloaded script bytes remains visible through the separate content fingerprint.

## Optional partner boundary

The existing partner document describes a possible technical integration pilot, not a signed order or an implemented adapter. Adapter work starts only after a vendor supplies a named owner, written interface permission, official documentation, authorized sandbox/export, event mapping, acceptance owner, and commercial path. This optional route does not block use of the evidence engine or the owned functional practice.

No vendor name or logo may be presented as integrated, compatible, endorsed, or partnered until the relevant vendor confirms that status in writing.
